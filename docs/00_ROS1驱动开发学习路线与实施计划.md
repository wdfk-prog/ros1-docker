## 阶段 C：AGV 数据链路与 Navigation（13～18）

目标不是转型成导航算法工程师，而是能够理解驱动数据怎样进入坐标变换、状态估计、建图、定位、代价地图和规划，并能沿这条链路定位接口问题。

第 12 章已经完成 `Twist`、`JointState`、`Imu`、`Odometry`、covariance、坐标系约定和差速底盘正/逆运动学，因此阶段 C 不再单独重复“Odometry、Encoder、IMU 与运动数据”，也不再单独设置 LiDAR/超声波消息接口章节。后续章节直接消费已经建立的数据契约，并在 SLAM / Navigation 章节中按上层真实需要解释传感器输入。

### 13：TF / tf2 与移动机器人坐标系

深入理解：

```text
map
 -> odom
 -> base_link
 -> sensor frames
```

重点：先区分 `/odom` Topic、`odom` 里程计坐标系和 `odom -> base_link` 变换，再理解刚体变换的平移/旋转、求逆和链式组合；继续深入 `TransformListener -> BufferCore -> TimeCache/StaticCache`、`lookupTransform()` 查链算法、时间插值、TF authority、extrapolation，以及“消息有 `frame_id` 不等于 TF 已经存在”。

### 14：URDF / Xacro / robot_state_publisher / joint_states

理解整机几何关系、link/joint、fixed joint 与运动关节如何建立机器人自身的 TF tree；在纯 URDF 基础上继续理解 Xacro 只是“生成 URDF 的 XML 宏预处理层”，掌握 property、macro、include、参数与条件展开。重点区分 Xacro 源文件、展开后的 URDF/`robot_description`、`joint_states` 运行时关节位置，以及 `robot_state_publisher` 如何分别把 fixed joint 发布到 `/tf_static`、把运动关节发布到 `/tf`。

### 15：robot_localization——从轮式里程计与 IMU 到机器人状态估计

理解 `ekf_localization_node` / `ukf_localization_node` 的输入输出契约、15 维状态、predict/correct、状态协方差 `P`、过程噪声 `Q`、测量 covariance，以及：

```text
map_frame
odom_frame
base_link_frame
world_frame
```

重点不是滤波器数学证明，而是回答：

- `/odom` 与 `/imu/data_raw` 中哪些字段真正应该融合；
- 为什么同一编码器推导出的 pose / yaw / twist 不能机械地全部当成独立信息；
- `two_d_mode` 如何把三维状态约束到二维 AGV；
- `frequency`、`sensor_timeout`、queue、时间戳如何影响 predict/correct；
- covariance 怎样影响观测权重；
- `world_frame=odom` 时为什么应由 `robot_localization` 独占 `odom -> base_link`。

本章实验把第 12 章 Driver 改为原始输入 `/odom/raw` + `/imu/data_raw`，输出 `/odometry/filtered`，并正式替换第 13/14 章教学用 `odom_tf_broadcaster`。

### 16：SLAM 与定位——地图、AMCL 与 `map -> odom`

把“建图”和“已有地图后的定位”放在同一条坐标链里理解：

```text
建图：
/scan + odom + TF
       -> SLAM
       -> /map + map -> odom

已有地图运行：
/map + /scan + odom + TF
            -> AMCL
            -> map -> odom
```

重点不是算法推导，而是谁消费哪些数据、谁负责 `map -> odom`、为什么连续的 `odom -> base_link` 与可能跳变的全局 `map -> odom` 必须分层；`LaserScan` 的 frame、时间和有效数据契约在真正进入 SLAM 时按需讲解，不单独拆成驱动接口篇。

### 17：Navigation / move_base

理解：

```text
localization
 -> costmap
 -> global planner
 -> local planner
 -> cmd_vel
```

重点是 global/local costmap、planner、机器人位姿、传感器障碍物和 `/cmd_vel` 之间的数据依赖，以及上游 TF / odom / sensor 错误如何传播到导航行为。`LaserScan` / `Range` / `PointCloud2` 在此只按 costmap 的真实消费关系解释，不回到“怎么写传感器 Driver”。

### 18：AGV 跨层故障定位

建立典型问题矩阵：

- 有传感器数据但 costmap 无障碍物；
- odom 连续但定位漂移；
- TF extrapolation；
- `cmd_vel` 正常但底盘行为错误；
- IMU 方向 / ENU-NED 错；
- 左右轮符号、单位、gear ratio 错；
- timestamp 延迟导致融合异常。

验收：从 Driver 的 Topic 和 frame 输出开始，能够沿 `Topic -> TF -> state estimation / localization -> costmap -> planner -> cmd_vel` 逐层缩小问题范围。
