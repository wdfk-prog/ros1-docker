## 阶段 C：AGV 数据链路与 Navigation（13～18）

### 16：SLAM 与定位——激光雷达、地图、AMCL 与 `map -> odom`

先从激光雷达的测距与扫描原理进入定位链路：解释二维扫描中的角度、距离、水平 FOV/角分辨率，以及 3D 多线 LiDAR 中常说的 16/32/64 线、垂直 FOV/通道角；二维数据落到 `sensor_msgs/LaserScan`，三维只先建立到 `sensor_msgs/PointCloud2` 的概念桥接，详细点云布局和 PCL 仍放在第 19～21 章。

随后把“建图”和“已有地图后的定位”放在同一条坐标链里理解：

```text
建图：
/scan + odom + TF
       -> SLAM
       -> /map + map -> odom

已有地图运行：
/map + /scan + odom + TF
            -> AMCL
            -> map -> odom
```

重点不是算法推导，而是谁消费哪些数据、谁负责 `map -> odom`、为什么连续的 `odom -> base_link` 与允许全局修正的 `map -> odom` 必须分层；`LaserScan` 的 frame、采集时间、角度和有效距离契约在真正进入 GMapping/AMCL 时讲清，并用最小二维墙体实验实际观察 `/scan`、`/map`、`/amcl_pose` 与 TF ownership。

### 17：Navigation / move_base

理解：

```text
localization
 -> costmap
 -> global planner
 -> local planner
 -> cmd_vel
```

重点是 global/local costmap、planner、机器人位姿、传感器障碍物和 `/cmd_vel` 之间的数据依赖，以及上游 TF / odom / sensor 错误如何传播到导航行为。`LaserScan` / `Range` / `PointCloud2` 在此只按 costmap 的真实消费关系解释，不回到“怎么写传感器 Driver”。

### 18：AGV 跨层故障定位

建立典型问题矩阵：

- 有传感器数据但 costmap 无障碍物；
- odom 连续但定位漂移；
- TF extrapolation；
- `cmd_vel` 正常但底盘行为错误；
- IMU 方向 / ENU-NED 错；
- 左右轮符号、单位、gear ratio 错；
- timestamp 延迟导致融合异常。

验收：从 Driver 的 Topic 和 frame 输出开始，能够沿 `Topic -> TF -> state estimation / localization -> costmap -> planner -> cmd_vel` 逐层缩小问题范围。
