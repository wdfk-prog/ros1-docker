# ROS1 驱动开发学习路线与实施计划

> 文档定位：本文件是 `wdfk-prog/ros1-docker` 后续学习内容的项目级 Source of Truth（学习范围、优先级、章节顺序、实验方式和验收标准）。后续新增教程、实验、源码阅读和调试任务，默认以本文件为依据；若后续需要调整路线，应先更新本文件，再扩展对应章节。

## 1. 项目目标与角色定位

本项目不以“完整掌握 ROS 上层应用开发”为目标，而以 **MCU + Linux ROS 驱动开发** 为主线，最终覆盖 AGV 与机械臂系统中驱动层必须理解的上层数据契约和调用关系。

目标角色定义为：

> 能从 MCU、CAN/UART/Ethernet、Linux 设备访问一路追踪到 ROS1 roscpp、Topic/Service/Action、TF、Navigation、ros_control、MoveIt 数据消费者，并能通过源码、GDB、rqt、rosbag、网络抓包和测试定位跨层问题的 ROS1 驱动工程师。

项目重点不是堆积 ROS API，而是建立以下完整认知链：

```text
MCU / Sensor / Motor / CAN Device
        |
        v
Linux Driver / SocketCAN / Serial / Ethernet
        |
        v
ROS Driver Node
        |
        +--> Topic / Service / Action
        +--> timestamp / frame_id / unit / frequency
        +--> diagnostics / reconnect / watchdog
        |
        v
TF / Odometry / Robot State / Navigation / Perception
        |
        v
ros_control / MoveIt / Manipulator
```

## 4. 学习原则

### 4.1 主线优先级

总体优先级固定为：

```text
ROS1 运行机制
    > ROS 驱动工程
    > AGV 数据链路与 Navigation 接口
    > 感知接口（PCL/OpenCV）
    > 机械臂接口（ros_control/MoveIt/Descartes）
    > 上层算法内部实现
```

这里的“优先级”不是表示后面的内容不重要，而是表示先建立与当前岗位最直接相关的依赖关系。

### 4.2 学习方式

后续每一章尽量采用同一模式：

```text
现象 / API
    ↓
最小可运行实验
    ↓
F12 找声明和实现
    ↓
F5 / GDB 跑进关键路径
    ↓
rqt / rosnode / rostopic / rosservice 观察
    ↓
必要时 tcpdump / Wireshark / strace
    ↓
加入测试或故障注入
    ↓
形成数据流与生命周期结论
```

不能只满足于“代码能运行”。对关键章节，应至少回答：

- 对象在哪里创建、由谁持有、何时销毁？
- 哪个线程执行？
- 数据在哪里排队？
- queue_size 实际约束什么？
- 什么时候发生序列化/反序列化？
- Master 参与到哪一步，什么时候退出数据通路？
- TCPROS 连接何时建立、断开、重连？
- Callback 为什么在当前时刻被执行？
- shutdown 如何传播？
- 时间戳、坐标系、单位和频率如何影响上层？

### 4.3 深度边界

本项目要求：

- roscpp、通信、线程、回调、驱动可靠性：**深入源码与运行机制**；
- TF、Odometry、Navigation、PCL/OpenCV、MoveIt：**理解数据契约和主调用链，能够跨层定位问题**；
- SLAM 数学推导、视觉算法研究、点云算法研究、MoveIt 规划算法内部优化：**非当前主线**，按工作需要扩展。

## 5. 总体实施顺序

## 阶段 A：ROS1 roscpp 运行机制（06～11）

这是现阶段立即开始的主线。

### 06：ROS1 Node 启动与生命周期

核心链路：

```text
main()
  -> ros::init()
  -> ros::NodeHandle
  -> NodeHandle::construct()
  -> ros::start()
  -> XMLRPCManager
  -> PollManager
  -> ConnectionManager
  -> TopicManager / ServiceManager
```

必须掌握：

- `ros::init()` 做了什么，没做什么；
- 为什么创建第一个 `NodeHandle` 会触发 `ros::start()`；
- 全局状态、内部 callback queue、内部线程的建立；
- SIGINT、`ros::ok()`、`ros::shutdown()` 生命周期。

验收：能用 F5/GDB 从 `hello_node.cpp` 进入上述关键函数，并画出启动/关闭时序。

### 07：Master、XML-RPC 与注册发现机制

核心链路：

```text
Node
 -> XML-RPC
 -> ROS Master
 -> registerPublisher / registerSubscriber
 -> publisherUpdate
 -> requestTopic
```

必须掌握：

- Master 是“发现/注册中心”，不是 Topic 数据中转站；
- Publisher/Subscriber 如何互相发现；
- 名称解析、namespace、remap 与 private namespace；
- Node API 与 Master API 的边界。

验收：能够结合 `rosnode`、`rostopic` 和断点说明两个 Node 从启动到互相发现的过程。

### 08：TCPROS、序列化与实际数据传输

核心链路：

```text
Publisher::publish()
 -> Publication
 -> Serialization
 -> Connection
 -> TransportTCP
 -> socket
 -> Subscriber
 -> Deserialization
```

必须掌握：

- TCPROS header negotiation；
- message datatype / md5sum；
- 序列化和发送队列；
- `TransportTCP`、`Connection`、`PollManager` 基本职责；
- `TCP_NODELAY` 与延迟；
- publisher/subscriber queue 的基本行为。

工具：GDB + `tcpdump` / Wireshark。

验收：能够同时用源码调用链和抓包解释 `/chatter` 一条消息如何从 Publisher 到 Subscriber。

### 09：CallbackQueue、Spinner 与线程模型

重点：

- `ros::spin()`；
- `ros::spinOnce()`；
- `SingleThreadedSpinner`；
- `MultiThreadedSpinner`；
- `AsyncSpinner`；
- global callback queue 与自定义 callback queue；
- callback 阻塞、共享状态、锁与驱动线程之间的关系。

验收：构造一个故意阻塞的 callback，通过日志和 GDB 解释为什么其它 callback 被延迟，并能给出适合驱动 Node 的线程模型。

### 10：Unit Test、rostest、rqt 与调试工具

`rqt` 不等到本章才第一次使用：从 `06` 开始，每章都可使用 `rqt_graph`、`rqt_console`、`rqt_plot`、`rqt_topic`；本章负责系统整理。

重点：

- gtest / `catkin_add_gtest`；
- rostest；
- Node 级集成测试；
- fake/mock 设备思路；
- rqt graph / console / plot / topic；
- rosbag 作为可重复输入和回归证据；
- 故障注入的基本方法。

验收：给一个 ROS Node 增加至少一组纯逻辑单测和一组 ROS 集成测试，并能使用 rqt/rosbag 辅助验证。

ROS-Industrial Session 6 的 Unit Testing 与 rqt 内容放在这里吸收，而不是等所有源码课程结束后再回头补。

### 11：Service 与 Action 的实现机制

重点：

- Service 建链和同步请求/响应；
- Topic 与 Service 的设计边界；
- actionlib 的 goal / feedback / result / cancel；
- 为什么机械臂轨迹执行、导航任务等更适合 Action。

验收：能够解释 Topic、Service、Action 在驱动和机器人控制中的适用边界，并追踪一个 Service 和一个 Action 的主要调用链。

## 阶段 B：ROS 驱动工程（12～18）

这是与当前岗位最相关的工程阶段。

### 12：ROS 驱动 Node 的软件架构

建立典型分层：

```text

    |

Transport
```

重点处理：ROS callback 与设备 I/O 解耦、生命周期、错误传播、状态机和线程边界。

### 13：CAN / Serial / Ethernet 与 ROS

以实际驱动常见链路学习：

- TCP/UDP/Ethernet；
- RX/TX thread；
- timeout；
- reconnect；

### 14：ROS 消息与驱动数据契约

重点消息：

- `sensor_msgs`；

- `geometry_msgs`；

核心不是背字段，而是理解每个字段的单位、坐标系、时间戳、协方差和消费者预期。

- 错误降级；
- reconnect；
- watchdog；

### 17：rosbag、Wireshark、tcpdump、strace 联合诊断

### 18：驱动测试体系

## 阶段 C：AGV 数据链路与 Navigation（19～26）

目标不是转型成导航算法工程师，而是能够理解驱动数据怎样进入定位、建图、代价地图和规划。

### 19：TF / tf2 与坐标系

必须深入理解：

```text
map
 -> odom
 -> base_link
 -> sensor frames
```

重点：frame_id、静态/动态 TF、时间查询、TF extrapolation。

### 20：URDF / robot_state_publisher / joint_state

理解整机几何关系和关节状态如何建立 TF tree。

### 21：Odometry、Encoder、IMU 与运动数据

重点：轮速、里程计、IMU、协方差、坐标系约定、符号和单位。

### 22：LiDAR、超声波、相机等传感器接口

重点关注驱动输出消息格式和上层消费者要求。

### 23：robot_localization 与传感器融合接口

理解 EKF/UKF 的输入输出契约、frame 配置、时间和协方差；不要求先深入滤波器数学证明。

### 24：SLAM 基础与驱动接口

理解 SLAM 需要什么传感器、TF、odom 和时间关系；算法推导按需扩展。

### 25：Navigation / move_base

理解：

```text
localization
 -> costmap
 -> global planner
 -> local planner
 -> cmd_vel
```

重点是数据依赖和故障传播。

### 26：AGV 跨层故障定位

建立典型问题矩阵：

- 有传感器数据但 costmap 无障碍物；
- odom 连续但定位漂移；
- TF extrapolation；
- `cmd_vel` 正常但底盘行为错误；
- IMU 方向/ENU-NED 错；
- 左右轮符号、单位、gear ratio 错；
- timestamp 延迟导致融合异常。

验收：从驱动输出开始，能够沿 Topic/TF/Navigation 数据链逐层缩小问题范围。

## 10. 风险与边界

### 10.1 ROS1 EOL

ROS1 Noetic 已 EOL，上游仓库可能处于归档/read-only 状态。本项目用于现有 ROS1 工程学习和维护；不要把 EOL 后第三方 fork 的行为默认当成 Noetic 官方行为。

### 10.2 “会 API”不等于“理解运行机制”

只有 API 示例不能作为阶段 A 完成依据，必须有源码路径或运行时证据。

### 10.3 “有 Topic 数据”不等于驱动正确

驱动必须同时关注：

- unit；
- sign / axis；
- frame_id；
- timestamp；
- frequency；
- covariance；
- sequence/lifecycle；
- timeout/reconnect；
- queue / latency。

### 10.4 Host 测试不等于硬件验证

fake/mock/rosbag 能覆盖协议和 Node 行为，但不能证明 CAN 总线时序、真实设备恢复、传感器噪声、执行器安全和硬件实时性正确。涉及真实设备时必须明确 Host、目标机、HIL 各自验证边界。

### 10.5 上层学习深度受岗位目标约束

MoveIt、PCL、OpenCV、Navigation 都需要学习，但当前目标是“理解输入、输出、关键状态和故障传播”，不是默认深入其全部算法实现。只有工作任务进入对应算法模块时再扩展专项计划。
